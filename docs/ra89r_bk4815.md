**Status: VALIDATED on the radio (branch `driver/bk4815`).**  Console `n`
confirms the identity (`0x4816`), the boot configuration, and the synthesizer
path: it tunes 145.7500 MHz through `0x71`/`0x72` (the word `0x8689d89d` lands
in those registers, `0x70 = 0xa000` RX, the VCO divider in `0x04`), and its own
`0x44` RSSI **responds to a carrier** (16 quiet → 41 keyed, back on release).
So the part receives; the SELCALL/tone paths below are still from the image and
the datasheet only.

The radio carries **two** BK481x transceivers.  This is the one on chip select
`PB13`; its sibling is the BK4829 on `PB8` (`ra89r_bk4829.md`).  The bus they
share, the boot bring-up order and the power path are in `ra89r_rfpath.md`.

## What the part is — the datasheet

The chip is a **Beken BK4815N**: a half-duplex TDD FM transceiver, 124–560 MHz,
with an integrated fractional-N synthesizer, 26 MHz crystal reference, PA and
FSK/DTMF/SELCALL/CTCSS signalling.  The datasheet
(`BK4815N_Datasheet_v1.0.1.pdf`, "Interface Register Definition", addresses in
**decimal**) is the authority for the register map, and it settles several
things this file previously guessed at:

| reg (dec / hex) | meaning |
|---|---|
| 0 / `0x00` | device id, reads `0x4815` on the datasheet part — this board's part answers `0x4816`, a variant |
| 12 / `0x0c` | PLL calibration + per-block power: `0x0603` RX, `0xF823` TX, `0xFFFF` idle |
| 13 / `0x0d` | IF selection: 88 kHz / 137 kHz |
| 24 / `0x18`, 25 / `0x19` | DTMF low / high tone, `(freq/18466)*65536` |
| 34 / `0x22` | **SELCALL tone frequency**, `(freq/18466)*65536` |
| 36 / `0x24`, 37 / `0x25` | CTCSS: high 2 bits + phase / low 16 bits, `(freq/18466)*65536*4` |
| 44 / `0x2c`, 45 / `0x2d` | audio AGC (`0x8A2E`/`0x1B80` defaults; the boot block writes `0x8A2F`/`0x1BC0`) |
| 67 / `0x43` | FM demod: **SNR indicator** (bits 12:0, 1 dB/step) |
| 68 / `0x44` | **RSSI/SNR**: RSSI indicator bits 6:0, 1 dB/step |
| 91 / `0x5b` | CTCSS symbol frequency, `(freq/18466)*65536*8` |
| 109 / `0x6d` | PA output power control, `0x4600` RX / `0x4700` TX |
| 112 / `0x70` | operation control, `0xA000` RX / `0xE000` TX |
| **113 / `0x71`, 114 / `0x72`** | **high / low 16 bits of the channel frequency word** |

The synthesizer formula is explicit in the datasheet: the locked frequency is
`Ndiv × (fwanted − fIF)` in RX and `Ndiv × fwanted` in TX, with the VCO-to-LO
divider `Ndiv` (8/12/16/24) in register 4 bits 8:7 and channel selection by the
fractional-N word in **registers 113/114 (`0x71`/`0x72`)**.  That is what the
stock programs (below); the `0x38`/`0x39` pair the BK4829 uses does not exist
here.

## What the stock does with it — the RF role

**The stock uses this chip as the receive path above 134.0 MHz.**  It is a
second receiver, not an IF/aux path and (in this build) not a transmitter.

* **The select flag is `0x20000303`.**  `FUN_08006360` sets it to `1` when the
  channel frequency is `<= 0x00CC77C0` (**134.01 MHz**) and to `0` above it;
  `FUN_08017340` sets it from a 560 MHz comparison first, so for every tunable
  channel the operative rule is `FUN_08006360`'s: `<= 134 MHz` → `1`, else `0`.
  The flag then routes *four* independent choices, all in this file's favour:
  * **per-mode config** — `FUN_08016EE0(chan, flag)` with `flag == 0` runs the
    BK4815 branch (`FUN_080187DA` writes `0x0c = 0x0A03`; `FUN_08016CEC` is the
    per-mode config), with `flag != 0` runs the BK4829 branch and *parks* the
    BK4815 (`FUN_080187CC` writes `0x0c = 0xFFFB`);
  * **T/R** — `FUN_08016228`/`FUN_08009CC4` write the BK4815's `0x0c`
    (`0x0203` / `0x0A03`) when `flag == 0`, and the BK4829's `0x47`/`0x13`/`0x30`/
    `0x31` when `flag == 1`;
  * **signal detect** — `FUN_08005440(chan, flag)` picks `FUN_08005218`
    (`flag == 0`), which reads the BK4815's **`0x43`/`0x44`** RSSI/SNR, over
    `FUN_080052B8` (`flag == 1`), which reads the BK4829's `0x63`/`0x65`/`0x67`;
  * **TX setup** — `FUN_08017306(chan, mode)` runs `FUN_080171D0` (BK4815) for
    `mode == 0` or `FUN_08017280` (BK4829) otherwise.

  So `<= 134 MHz` is BK4829, `> 134 MHz` is BK4815 — including the whole 2 m and
  70 cm ranges (144–146 and 430–440 MHz) and the upper half of the stored VHF
  range (108–174).
* **The BK4815 is a real receiver with its own metering.**  `FUN_08005218`
  reads `0x44` (`(reg & 0x3fff) >> 8`) and `0x43` (`reg & 0xfff`) — the
  datasheet's SNR/RSSI indicator fields — and returns the same 0/1/2 squelch
  verdict the BK4829's routine does.  The chip is read back at `0x43`/`0x44`
  only, never the BK4829's `0x63`/`0x65`/`0x67`, so the metering is genuinely
  this part's own.
* **The stock never transmits through it.**  `FUN_08018AB8`, the transmit
  entry, calls `FUN_08017306(chan, 1)` with the argument **hard-coded to 1**, so
  the TX setup always selects the BK4829's `FUN_08017280`.  The BK4815's own TX
  setup `FUN_080171D0` (`0x0c = 0xF823`, `0x6d = 0xE718`, the datasheet's TX
  values) is reached only from `FUN_08017306(mode == 0)`, and that branch has no
  caller in the image: **it is dead code**.  (Checked: the only `bl` to
  `FUN_08017306` is `0x08018AEE`, which passes `1`; there is no function-pointer
  literal to `FUN_080171D0` either.)
* The T/R path does still write the BK4815's `0x0c = 0x0203` above 134 MHz while
  keying, so the part is at least toggled out of its `0x0A03` receive state; but
  its PA register `0x6d` is only ever written with the **receive** value
  `0x6618` (`FUN_08016CEC`), never the TX `0xE718` of the dead routine.

**Reading, with the uncertainty kept:** statically, the BK4815 is the
> 134 MHz **receiver** and the BK4829 is the transmitter for every band.  That
the BK4815's PA/transmit hardware exists (datasheet, and the dead routine's
register values) but the stock never enables it is an inference from the call
graph, not a measurement.  It would be settled with a scope on the two chips'
TX-enable pins, or by forcing `FUN_08017306`'s second argument to `0` in a
patched stock image.  It is also *not* the same thing as the earlier
"BK4829 carries the whole TX setup for both bands" reading in
`ra89r_rfpath.md`, which mistook `FUN_08017280`'s callers for unconditional:
`FUN_08017306` chooses, and always chooses the BK4829.

## The frequency path — registers `0x71`/`0x72`, not `0x22`

`FUN_0801703C` is the stock's BK4815 frequency writer.  It runs from the
per-mode configs `FUN_08016CEC` (RX) and `FUN_080171D0` (TX) and does, in order:

```
FUN_08022082(FUN_0800EC70(chan) << 7 | 0xB041, 4)   -- VCO divider into reg 4
write 6 bytes at reg 0x70:
    [0xA0/0xE0, 0x00, word_hi16, word_lo16]   -- 0x70 op-ctrl, 0x71/0x72 word
write 4 bytes at reg 0x7E: the per-band calibration word
```

with the word computed in soft-float as

```
word = (freq_10Hz / 100000) * Ndiv * 2^24 / 26
```

(the double constants are `100000.0` at `0x08017148` and `2^24/26 =
645277.538…` at `0x08017150`), i.e. `freq_Hz * Ndiv * 2^24 / 26e6` — exactly the
datasheet's `Ndiv × fwanted / 26 MHz × 2^24`.  It **omits the RX IF offset** the
datasheet mentions; that is the stock's choice, copied here.  The VCO band comes
from `FUN_0800EC70` with thresholds `0x011D56E0` / `0x019BFCC0` / `0x02486960`
= 187 / 270 / 383 MHz, and its divider table is `(band 0:8, 1:16, 2:12, 3:24)`
— register 4 bits 8:7.  The per-band calibration words `FUN_0801703C` writes to
`0x7E`/`0x7F` are `0xFFF53568`, `0xFFEA6AD0`, `0xFFEFD01C`, `0xFFDFA037`; band 0's
is exactly the boot configuration's `0xFFF5`/`0x3568`, which is a useful check
that the routine and the boot block address the same register pair.

**Correction to the earlier reading.**  An earlier version of this file said the
chip's "tuning word goes to register `0x22` as `(x << 16)/0x4822`".  That is
wrong on the register: **`0x22` (register 34) is the SELCALL tone frequency**,
and the `(freq/18466)*65536` encoding is the datasheet's signalling-tone
formula, with `0x4822` = 18466 the shared divisor it also uses for CTCSS/DTMF.
The routine that writes it, `FUN_08005C34`, is the BK4815 half of the stock's
tone player: it is the exact sibling of `FUN_08005D2C`, which writes the
**BK4829's** tone register `0x71` with the K1's `scale_freq` (`freq * 10.32444`,
the double at `0x08005D7C`).  The two are called with the same arguments from
the same dispatcher (around `0x08007A2C`/`0x08007A8C`), selected by the config
byte at `0x20009F28 + 0x1f`, so they are the same feature on the two chips, not
the RF tuning.  The real tuning is the `0x71`/`0x72` block above.

The driver now has both: `bk4815_set_frequency()` (regs 4/0x70/0x71/0x72/0x7E)
and `bk4815_set_tone()` (reg `0x22`), with the encodings above.  The host test
`firmware/tools/test_rf.c` checks the VCO bands, the word for 108/145.75/230/
320/446/520 MHz and the tone words.

## Identity and wiring

| | |
|---|---|
| chip select | `PB13` — GPIOB mask `0x2000`, active low |
| clock | `PA12` (shared with the BK4829) |
| data | `PB12` (shared, bidirectional) |
| register 0 | reads **`0x4816`** |

`FUN_08009758` is the stock's identity check: it is one call to
`FUN_08018060(0)` — this chip's read of register 0 — compared against `0x4816`.
On failure `FUN_08006A0C` calls `FUN_08015D14(0x0b)` and returns without
configuring the chip.  (Both chips' inits pass the **same** error code, which is
why the two error strings cannot simply be split one per chip — see
`ra89r_rfpath.md`.)

**Its framing differs from the BK4829's.**  This chip is addressed with
`(reg & 0x7f) << 1` to write and `((reg & 0x7f) << 1) | 1` to read — the
address byte carries the register shifted left, with bit 0 as the read flag —
whereas the BK4829 puts the read flag in bit 7 and sends the register unshifted.
The register layer is `FUN_08022082(value, reg)` for writes and
`FUN_08018060(reg)` for reads, wrapping `FUN_08021F78` on the shared
`PA12`/`PB12` bit layer (`ra89r_rfpath.md`).

`FUN_08021F78(buf, reg, len)` writes `len` bytes starting at one register
address, so a whole block goes out under a single select pulse — which is how the
stock loads this chip's 18-register table (below).

Three writes take their value from RAM rather than a constant — registers
`0x4c`, `0x55` and `0x62`, read from `0x2000449a`, `0x2000449c` and
`0x2000449e`.  Those are calibration-shaped fields loaded earlier in the boot;
where the boot code gets them from is open.

One decompiler artifact to be aware of: the write of `0x8000` to register `0x40`
comes out of the decompiler as a one-argument call, `FUN_08022082(0x8000)`.  The
disassembly shows why — the compiler reuses a register, `movs r1, #0x40` then
`lsls r0, r1, #9` — and the register really is `0x40`, as the table says.  Do not
read the missing argument as "register 0".

**What `FUN_08016CEC` really is (decompiled 2026-10-18):** not a six-write
"squelch setup" but the **per-VFO receive entry**, which does everything
together and therefore is the reference for "what a frequency change does":

1. `FUN_08011b74(0x48000000, 0x4000, 0)` = `GPIOA->BRR = 0x4000` -- PA14 low
   (the stock's LED line), not an RF path.
2. `FUN_0801703c(vfo)` -- the tune: `0x04 = band << 7 | 0xb041`, the 6-byte
   block at `0x70` (`0xa0` RX / `0xe0` TX, then the word) and the 4-byte
   calibration block at `0x7e`.  Per-band (band, Ndiv, cal) = (0, 8,
   `fff53568`), (1, 16, `ffea6ad0`), (2, 12, `ffefd01c`), (3, 24, `ffdfa037`)
   -- **exactly the port's `cal[]` and `bk4815_vco_divider()`** (checked
   against the literals at `0x08017138`-`0x08017150`).
3. `0x16 = b200`, `0x2b = 403f`, `0x6d = 6618`, `0x73 = 81d0`.
4. `FUN_08016f28(0x226, 2)` -- `0x5b = 0x2616` (the `param_2 == 1` branch is
   `0x25 = (freq << 18 / 0x4822) / 10`, rounded).
5. `FUN_08006e4c(vfo[0x91])` -- **`0x01 = 0x0044` (12.5 kHz) when the field
   is 2, else `0x8044` (25 kHz)** (re-read in Ghidra 2026-10-27; this line used
   to say the reverse).  The CPS stores bandwidth 0 wide, 1 mid, 2 narrow, so
   the stock's narrow is `0x0044` -- what the port's `bk4815_receive_entry()`
   writes for a narrow VFO; its "mid" maps to narrow in the port, `0x8044` in
   the stock.
6. `FUN_08019df4(vfo[0x77])` -- **`0x48 = a002` for profile 0, else
   `0x48 = 8002` + `0x4a = table[profile - 1]`**: a per-VFO AF profile; the port
   leaves `0x48` at the boot table's `a002` and never writes `0x4a`.
7. `FUN_0800b520(profile)` -- the compander: `0x4c = 6506`/`0x4e = 800f` for
   profile 0, else `0x57 |= 8000 | n`; reads `0x73` and ORs `0x400`
   (profile 0) or `0x200`; writes `0x42`; profile 0 walks `0x4d` with two
   16-entry coefficient tables.  The port writes none of this per VFO.
8. `FUN_08013790(band)` -- `0x75 = (read & 0xffc0) | {0x11 band 1, 0x0a band 2,
   0x12 band 3, 0x09 band 0}`; `FUN_08016CEC` collapses it to `0x0a` when the
   VFO's band field is 1 or 2, else `0x11`.  Note the **read-modify-write**
   (bits 15:6 preserved); the port writes the whole word.
9. `FUN_080137d4(0x10, 0x10)` -- read-modify-write of `0x33`: pin mask `0x10`
   selects pin 4, value `0x10` sets it, the output bit is `0x40 >> 4 = 0x04`
   and its paired bit `14 - 4 = 10` is cleared.  The port's
   `BK4819_GPIO4_PIN32_VHF_LNA` writes the same bit.
10. `0x70 = 0`, `0x70 = a000` -- the restart pair.

The per-VFO pieces the port lacks are therefore **`0x01` (bandwidth),
`0x48`/`0x4a` (AF profile) and the compander block (`0x42`, `0x4c`, `0x4d`,
`0x4e`, `0x56`, `0x57`, and the `0x73` compander bits)** -- all *located*; none
verified on the radio.

### What the port's BK4815 receive lane needs (radio-validated 2026-10-19)

Five faults turned a correctly-tuned, carrier-bearing BK4815 VFO into "squelch
open, only noise" or into silence.  They are fixed on develop (`driver/rx`
merge `b692aff`); the details are in `driver/rx.c`'s comments:

1. **The scan leaves the part on a probe.** `chFrScanner`'s `ScanBothProbe()`
   tunes the chips directly, and when the scan ended nothing retuned them
   (the applied-state check only notices *known* changes).  Measured: VFO
   145.500 with the tune word reading 146.25000 (the last probe).  The applied
   state is now invalidated on scan-override entry/exit and on a VFO switch,
   so returning to the VFOs re-applies them like a frequency change does.
2. **The band register `0x75` and the receive-path pin are written behind the
   port's back** -- `pa_select_band()` writes `0x75` from whatever frequency
   it is handed (the BK4829's, on its retunes), and the K1's RF setup clears
   the pin.  `rf_dual_refresh()` now owns both, written on change after every
   pass's retunes.
3. **The unassigned BK4829 is the audio path, and off-channel it is a noise
   source.** With both VFOs on the BK4815 the 4829 has no VFO; the bridge
   opens its AF while the BK4815's squelch is open, and the BK4815's audio
   rides that same RX/AF chain.  The state that worked had the 4829 on the
   *same channel* (good capture: 446.00625, RSSI 281; noisy one: 145.5000).
   Its tune is now mirrored onto the BK4815's whenever no VFO names it.
   (Parking its demodulator silenced the receiver completely -- its RX chain
   is required for the 4815's audio, which is what proves the topology.)
4. **The first reception after idle opened onto a slept BK4829** (`0x30 = 0`,
   `0x37 = 0x1D00`): the K1 only wakes it in its own receive path, so the
   first carrier was noise and the second fine.  `rx_poll()` now calls
   `BK4819_RX_TurnOn()` on the squelch-open edge.
5. **The part's RSSI scale is not the same by band**: the same carrier reads
   47-58 on 446.00625 and 32-33 on 145.5, while the marks were a fixed
   open 30 / close 24.  The VHF pair is now open 20 / close 14.

Still open: the marks are a documented ladder from the level-8 point that was
measured, not the stock's calibration.  The stock derives its squelch threshold
from the per-frequency squelch page at external flash `0x3710` (and the RSSI
page at `0x3860`) through `FUN_0800E3F6`/`FUN_0801D568`; decoding that table is
the proper follow-up (`docs/ra89r_calibration.md`,
`docs/superpowers/plans/2026-10-21-rx-sensitivity-and-scan-throughput.md`).

Several patterns stand out, and the datasheet now names most of them.  Register
`0x0c` takes a family of related words (`0x0a03`, `0x0203`, `0xf823`, `0xf023`) —
the same register the T/R path flips, and the datasheet's PLL-calibration/mode
register (`0x0603` RX / `0xF823` TX / `0xFFFF` idle).  Register `0x70` is cleared
and then set to `0xa000` in both `FUN_08005C34` and `FUN_08016CEC` — the shape of
a power-down/up toggle, and `0xA000` is the datasheet's operation-control RX
value.  `0x75` is read-modify-written with `| 0x200` and `0x73` with
`| 0x8000`/`| 0x81d0`, i.e. bit flags rather than whole rewrites.  `FUN_08006D10`
writes the CTCSS group (`0x59 = 0xf7a1` is the datasheet's CTCSS detection speed,
`0x5b`/`0x5c`/`0x5d` the CTCSS symbol registers), and `FUN_08016F28` computes the
CTCSS words for `0x25`/`0x5b` with the same `/18466` scaling the datasheet gives.

Two of these need a caution:

* **`FUN_080171D0` is the BK4815's transmit-mode config and it is dead code.**
  It is reached only through `FUN_08017306(mode == 0)`, and every caller of
  `FUN_08017306` passes `1` (see "What the stock does with it").  Its values are
  still worth having — `0x0c = 0xF823` and `0x6d = 0xE718` are the datasheet's
  TX mode — but the stock never sends them.
* **`FUN_08005C34`'s `0x22 = (param << 16) / 0x4822` is a signalling tone, not
  the RF word.**  The datasheet's register 34 is SELCALL tone frequency,
  `(freq/18466)*65536`, with `0x4822` = 18466; the RF word is the `0x71`/`0x72`
  block `FUN_0801703C` writes.  The earlier "computed PLL/N-divider-style value"
  reading of this register is withdrawn.

`FUN_08006D10`'s `0x59 = 0xf7a1` matches the boot init's `0x59` exactly, which is
a useful confirmation that these routines are addressing the same part.

## The driver

`firmware/App/driver/bk4815.c` / `.h` on branch `driver/bk4815`, alongside the
BK4829's.  The shared 3-wire bus was split out of the BK4829 driver into
`firmware/App/driver/rf_bus.c`, which takes the chip select as a parameter and
now drives both; the two register layers stay separate because the frames differ.

Beyond the boot replay, the driver now carries the two encodings the image
supports, with the datasheet as the cross-check:

* `bk4815_set_frequency(freq_10hz, tx)` — `FUN_0801703C`'s three writes: the VCO
  divider into register 4, the `[0xA0|0xE0, 0x00, word_hi, word_lo]` block at
  `0x70`, and the per-band calibration block at `0x7E`.  The helpers
  `bk4815_vco_band()` (the 187/270/383 MHz thresholds), `bk4815_vco_divider()`
  (8/16/12/24) and `bk4815_frequency_word()` (`freq_Hz * Ndiv * 2^24 / 26e6`)
  are exposed so the host test can check them without a bus.
* `bk4815_set_tone(tone_hz)` — the `0x22` SELCALL word, `(freq/18466)*65536`.
* `bk4815_receive_entry(wide)` — the rest of `FUN_08016CEC`, the stock's per-VFO
  receive configuration, written **after** the tune and only on a lane
  (re)configuration (a VFO switch or a frequency change), never per scan probe:

  | reg | value | what the datasheet calls it |
  |---|---|---|
  | `0x16` | `0xB200` | VOX module (the stock writes it on receive entry) |
  | `0x2B` | `0x403F` | RAMP: up/down enable and speeds |
  | `0x6D` | `0x6618` | PA output power control, the receive value |
  | `0x73` | `0x81D0` | interrupt mask (link-loss, CTCSS/CDCSS-loss enables) |
  | `0x01` | `0x8044` / `0x0044` | common: channel spacing 25 / 12.5 kHz |
  | `0x70` | `0x0000`, then `0xA000` | the receive restart pair |

  The `0x01` bit is chosen from the VFO's `CHANNEL_BANDWIDTH` (the stock picks
  12.5 kHz when its channel byte `0x91 == 2`, narrow).  The stock's remaining per-VFO writes —
  `0x5B` (CTCSS symbol), `0x48`/`0x4A` (AF profile) and the compander block
  (`0x42`, `0x4C`–`0x4E`, `0x56`, `0x57`, `0x73`) — are **not** replayed yet;
  they are audio, not RF gain, and are their own feature.

  Gain is not per-VFO on this part: the boot block's `0x67 = 0xC31F` already
  fixes the datasheet's REG103 to RX AGC disabled, LNA high gain and IF PGA
  +21 dB, which is maximum gain.

Neither has been run on the radio yet; both are checked by the recording-bus
host test (`firmware/tools/test_rf.c`, and `test_rf_dual.c` for the receive
entry), which verifies the VCO bands, the words for 108/145.75/230/320/446/520
MHz, the tone words, and that the receive entry writes the registers above in
the stock's order.

`bk4815_configure()` sends the 36-byte block as **one** transfer (what
`FUN_08021F78` does) followed by the 33 single writes.  Three of those —
`0x4c`, `0x55`, `0x62` — are the ones the stock takes from its own RAM, so they
go out as `0` and both the source and the console say so; they need a source
before this configuration can be called complete.

On the radio this chip answered `0x4816` from register 0 on the first `R`, and
still answered it after `W` had sent the block and all 33 writes -- so the
shifted address encoding, the `PB13` select and the sequencing are all confirmed
on hardware, not just against the recording stub.  `X` then read every written
register back: **31 of the 33 store and return exactly what was sent**, and the
18-register boot block comes back 18 of 18.  The two
that do not are documented — `0x44` and `0x49` never read back what is written
and their high bits change on their own, i.e. they carry status bits
(`ra89r_bk4829.md`).  **The `0x49` case is now explained by the datasheet**:
REG73 is `[15]` hard mute, `[14:07]` **read-only RX audio level**, `[03:00]`
volume — a read never equals the written word by design, and bits 14:07 are a
usable demod-audio level meter (console `7` samples it to tell "the demod
produces audio" from "the gates are shut").

A read-only dump of a freshly booted part gives its **power-on defaults**, not the
stock's configuration — the decisive evidence is register `0x0C` reading `0xFFFF`
while the stock's boot init always writes `0x0A03` to it, and our own write to
`0x0C` afterwards reads back correctly.  Getting this firmware into flash means
entering update mode, so both parts are reset by the time this firmware runs, and
the three placeholder registers below cannot be recovered by reading:
`0x4c = 0x64A4`, `0x55 = 0x70A6` and `0x62 = 0x0003` are the *defaults*.  Their
real values come from the stock's RAM (`0x2000449a`/`9c`/`9e`), so they need that
chain traced, not a read-back.

## Open

1. **No radio validation of the new paths.**  The chip answered `0x4816` and
   accepted the boot configuration (above), but the synthesizer and tone writes
   have only been checked against the recording-bus host test.  In particular,
   whether the part actually locks on `bk4815_set_frequency()`'s word, and
   whether it radiates at all, are unmeasured.
2. **The RF role is a call-graph finding, not a measurement.**  The stock powers
   the BK4815 up and configures it above 134 MHz, uses its `0x43`/`0x44` meters
   for the squelch, and never reaches its TX setup (`FUN_080171D0` is dead).
   That reads as "receive-only second receiver above 134 MHz", but the part is a
   transceiver and the T/R path does write its `0x0c`.  To settle it: scope the
   two chips' TX-enable/PA lines, or patch `FUN_08017306`'s second argument from
   `1` to `0` and watch the BK4815's `0x6d`/PA path.
3. **Why the crossover is 134.0 MHz.**  It sits inside the stored VHF range, not
   on a band edge; `FUN_08006360` is the setter, but why the design splits there
   is not explained by the image.
4. The three RAM-sourced registers (`0x4c`, `0x55`, `0x62`): where does the boot
   code get those values?  Partly answered by context — `FUN_0800B520` writes
   `0x4c`/`0x4d`/`0x4e`/`0x56`/`0x57` from a table and a read of `0x73`, so
   `0x4c` belongs to a calibration/table-driven group rather than being a
   per-band constant.  Until then the driver sends 0 for them.
5. **Registers `0x7E`/`0x7F`.**  `FUN_0801703C` writes them from a per-band
   constant, and band 0's value is the boot block's.  The datasheet's table
   stops at register 123, but all four constants decode to -137 kHz in their
   band's word units: they are the RX IF offset (2026-10-30, top note).
6. **The `0x4816` variant.**  This board's part answers `0x4816`, not the
   datasheet's `0x4815`, and the stock's mode words (`0x0A03`/`0x0203`) do not
   match the datasheet's (`0x0603`/`0xF823`) bit for bit, so the mode-register
   bit fields are not confirmed for this part.
7. ~~The stock's frequency word **omits the RX IF offset** the datasheet
   prescribes.~~  Answered 2026-10-30: the IF is applied through `0x7E`/`0x7F`
   (-137 kHz in every band), and `0x75` bit 10 must be 1 (low-side) for the
   part to receive the programmed frequency (note at the top).

## Port note: squelch 0 must open the BK4815 too (2026-10-11)

The BK4829's squelch is configured *in the chip* from `gEeprom.SQUELCH_LEVEL`
(`RADIO_ConfigureSquelchAndOutputPower()`), so level 0 forces the thresholds to
zero and the audio is always open.  The BK4815's audio is gated in software in
`driver/rx.c` (`rx_poll()`), and that gate used only the fixed
`RX4815_SQUELCH_OPEN/CLOSE_MARK` constants — so a BK4815 VFO stayed muted below
the fixed mark even with the user's squelch set to 0.  `rx_poll()` now forces
the lane open when `SQUELCH_LEVEL == 0`, mirroring the BK4829.
