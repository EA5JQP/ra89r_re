# BK1080 FM receiver

**Status: identified and mapped from the stock image; a register-layer driver
and a host test exist on branch `driver/bk1080`.  Nothing on this bus has run on
the radio, so every hardware claim here is *located*, not validated.**

The RA89R carries a **BK1080** FM broadcast receiver (65–108 MHz,
`docs/BK1080.pdf`) on its own two-wire bus.  This is the part that
`docs/ra89r_battery.md` first read as a "companion battery gauge"; that
identification was wrong, and this file is the FM side of it — the framing, the
register map the stock uses, the init sequence, the tuning word, and the
seek/status path.

The correction is worth stating up front because the earlier note is otherwise
easy to follow into a dead end:

| earlier reading (ra89r_battery.md) | what the evidence actually is |
|---|---|
| register `0x0B` is RSSI/status | `0x0B` is **Read Channel** (`READCHAN[9:0]`); `0x0A` is the RSSI/status register |
| the `875 / 760 / 640` "gauge offsets" are a divider zero point | they are the BK1080's **band bases**, 87.5 / 76.0 / 64.0 MHz |
| `(raw + offset) * 10000` is microvolts (10 mV/count) | it is the **tuned frequency in 10 Hz units** (100 kHz per channel) |
| `FUN_08006F9C` is a "voltage write-back" | it is the **tune**: it writes BAND/SPACE/VOLUME and CHAN/TUNE |
| the 68-byte block + register `0x32` are a gauge configuration | they are the BK1080's power-up register image (see below) |

The owner's teardown has no gauge IC on the board (BK4815, BK4829, BK1080,
TDA2822, LM2904B and a Jieli BT chip), and every register the stock reads on
this bus is a BK1080 register.  That is what settles it.

## The part and the pins

| | |
|---|---|
| part | BK1080 FM receiver, 65–108 MHz, `docs/BK1080.pdf` |
| clock | `PC14` (`GPIOC`, mask `0x4000`) — output, idles low |
| data | `PB2` (`GPIOB`, mask `0x4`) — **bidirectional**, driven to send, released to read |
| device id | `0x80`, a fixed byte the stock clocks out before every control word |

`FUN_0800D434` is the bus bring-up: it enables the GPIOB and GPIOC clocks
(`RCC_AHB2ENR` bits 3 and 4) and configures `PB2` (mask `4`) and `PC14` (mask
`0x4000`) as outputs.  That is the same function `ra89r_rfpath.md` sees at the
end of the RF bring-up, so the "gauge bus" is established there.  Every
bus primitive resolves to those two pins — `FUN_08006EF0` (start),
`FUN_08006F4C` (stop), `FUN_08006E78` (read a byte), `FUN_0800705C` (write a
byte), `FUN_08007158` (read), `FUN_08007240` (write) all load `GPIOC/0x4000`
and `GPIOB/4`, and `FUN_0800D138` reconfigures `GPIOB/4` for direction.

## The I2C framing

The BK1080's bus is not standard I2C: the device id is a fixed `0x80` byte and
the read flag rides in the register control word, `(reg << 1) | R/W`
(datasheet §6.2.2).  That is byte for byte what the stock emits.

| stock address | what it does |
|---|---|
| `0x08006EF0` | **start**: clock low, data high, clock high, then data **low** while the clock is high |
| `0x08006F4C` | **stop**: clock low, data low, clock high, then data **high** |
| `0x08007034(reg, rw)` | the address phase: start, `0x80`, `(reg & 0x7f) << 1 \| rw` |
| `0x0800705C(byte)` | write a byte MSB first, then release the line and poll it low (up to 250 times) for the acknowledge |
| `0x08006E78()` | read a byte MSB first, sampled while the clock is **high** |
| `0x08007158(reg, len, buf)` | read: address phase, then `len` bytes' worth of 16-bit words, high byte first |
| `0x08007240(reg, len, buf)` | write: address phase, then `len` bytes |
| `0x08007284(reg, value)` | 16-bit write: packs the value high byte first and calls `FUN_08007240(reg, 2, …)` |
| `0x0800D138(dir)` | data pin direction: output (1) or released (0) |
| `0x0802422A(n)` | the delay helper: a fixed `(n + 1) x 21` cycle loop, not a time |

Three details that cost time elsewhere and are easy to get wrong here:

* **The read samples on the high half of the clock.**  `FUN_08006E78` raises the
  clock, samples `PB2`, then drops it; the 3-wire RF bus (`rf_bus.c`) samples on
  the *low* half.  The phases are opposite.
* **The master drives the ACK bits.**  `FUN_08007158` pulls the data line low
  (ACK) after the first byte of every word and releases it high (NACK) after the
  last byte of the last word.
* **A word is two bytes, high byte first**, on both read and write — the same
  order the BK4829/BK4815 use, and the same order the stock's `FUN_08007284`
  packs (`value >> 8` stored first).

The stock never checks the acknowledge on a write (`FUN_08007240` ignores the
return) and discards the device-id ACK in `FUN_08007034`; only the control-word
ACK is returned, and nothing looks at it either.  A silent part would therefore
look exactly like a working one from the stock's point of view — which is why
the port's own bring-up has to poll a register it *does* read.

## The register map the stock uses

The public map is datasheet table 11.  The stock touches only these:

| reg | name | stock use |
|---|---|---|
| `0x00`–`0x21` | register file | written by the 68-byte init block (`FUN_08007124`) |
| `0x02` | Power configuration | read-modify-written to start a seek (`FUN_08006952`) and clear it (`FUN_08006982`) |
| `0x03` | Channel | read-modify-written to clear TUNE (`FUN_080069A6`); written by the tune (`FUN_08006F9C`) |
| `0x05` | System config 2 (SEEKTH/BAND/SPACE/VOLUME) | read for BAND (`FUN_0800687C`); written by the tune |
| `0x07` | Test 1 (FREQD + SNR) | read for SNR (`FUN_0800693C`) |
| `0x0A` | RSSI status (STC/SF-BL/AFCRL/STEN/ST/RSSI) | read for the seek result (`FUN_080068E8`) |
| `0x0B` | Read channel (IMPC + READCHAN) | read for the tuned channel (`FUN_0800687C`) |
| `0x32` | *beyond the public map* | written twice by the init (`FUN_08007124`) |

**The stock never reads register `0x01` (the chip id) and has no identity check
for this part**, unlike the BK4829 (`0x4829`) and BK4815 (`0x4816`).  A liveness
probe has to be added deliberately; the driver offers `bk1080_read_id()` for
that, labelled as not something the stock does.

## The init sequence — `FUN_08007124`

The BK1080 is powered up by a single 68-byte block written to register 0 (the
part auto-increments through registers `0x00`–`0x21`), followed by two writes to
register `0x32`:

```
FUN_08007240(0, 0x44, block)     -- 68 bytes into register 0
FUN_0802422A(100)                -- busy-wait
FUN_08007284(0x32, 0x285c)
FUN_0802422A(100)                -- busy-wait
FUN_08007284(0x32, 0x28dc)
```

The block's register `0x02` is `0x0201`, i.e. **ENABLE = 1** (bit 0) and
SEEKUP = 1 (bit 9).  That is the only place in the whole image where ENABLE is
set — the seek/status helpers never touch it — so this block is the BK1080's
power-up.

The 68 bytes are **RAM, not flash**.  `FUN_08007124` loads the literal
`0x20000088` (the pointer word at `0x08007154`), and that RAM is filled at boot
by the scatter table at `0x08027728`:

```
entry 0: src 0x08027748 -> dst 0x20000000, len 0x34c, decompressor FUN_0800483A
entry 1: src 0x0802796c -> dst 0x2000034c, len 0xc0e4, decompressor FUN_08023930
```

`FUN_0800483A` is a small LZ (literal runs plus back-references and zero runs;
the control byte's low 3 bits and high nibble are the two run lengths, with a
zero field reading a full byte, and bit 3 chooses a back-reference).
Decompressing entry 0 gives the block at offset `0x88`:

```
00 08 10 80 02 01 00 00  40 c0 0a 5d 00 2e 02 ff
5b 11 00 00 41 1e 00 00  ce 00 00 00 00 00 10 00
31 97 00 00 13 ff 98 52  00 00 00 00 00 08 00 00
51 e1 28 dc 26 45 00 e4  1c d8 3a 50 ea f0 30 00
00 00 00 00
```

Read big-endian it is a full register image: register 1 = `0x1080` (the chip
id), register 2 = `0x0201`, register 5 = `0x0a5d` (SEEKTH = 0x0a, BAND = 01,
SPACE = 01, VOLUME = 0xd), and so on.  It writes several read-only registers
(1, 10, 11) with plausible values, which is the signature of a vendor-supplied
register blob — exactly what the datasheet says the internal test registers
(`0x10`–`0x1f`) need ("initial value and procedure will be provided separately
by BEKEN").  The block's fields are **not** mapped beyond the few above.

**Register `0x32` is outside the public map** (table 11 stops at `0x1f`), so the
two values `0x285c`/`0x28dc` are vendor-internal.  They are recorded verbatim,
not explained.

## Tuning — `FUN_08006F9C`

`FUN_08006F9C(freq)` takes the firmware's usual **10 Hz units** and does the
whole tune:

```
ch100 = freq / 10000                       -- 100 kHz units
if ch100 < 760:  base = 640, band = 0xc0   -- BAND = 11 (64-76 MHz)
else:            base = 760, band = 0x40   -- BAND = 01 (76-108 MHz)
band |= 0x1f                               -- SPACE = 01 (100 kHz), VOLUME = 0xf
chan  = ch100 - base                       -- 10-bit CHAN
write reg 5 = 0x0a00 | band                -- SEEKTH = 0x0a
write reg 3 = chan
write reg 3 = 0x8000 | chan                -- TUNE | CHAN
```

So the tuning word is `{ BAND, SPACE = 100 kHz, VOLUME = max, SEEKTH = 10 }` in
register 5 and `CHAN` + `TUNE` in register 3.  Worked examples:

| frequency | `ch100` | band | `reg 5` | `reg 3` |
|---|---|---|---|---|
| 100.0 MHz | 1000 | 01 (76 base) | `0x0a5f` | `0x80f0` |
| 87.5 MHz | 875 | 01 (76 base) | `0x0a5f` | `0x8073` |
| 70.0 MHz | 700 | 11 (64 base) | `0x0adf` | `0x803c` |

The arithmetic is exact against the datasheet's
`Freq = spacing x channel + base` (`0.1 MHz x 240 + 76 = 100.0 MHz`).

## Reading the tuned frequency — `FUN_0800687C`

```
read reg 0x0b -> word;  READCHAN = word & 0x3ff
read reg 0x05 -> word;  BAND = (word >> 6) & 3
base = BAND == 0 ? 875 : (BAND == 1 or 2) ? 760 : 640
return (READCHAN + base) * 10000        -- 10 Hz units
```

The `875 / 760 / 640` here are the **band bases in 100 kHz units**, one per
datasheet BAND setting — not gauge offsets.  `(READCHAN + base) * 10000` in
10 Hz units is exactly `READCHAN * 100 kHz + base`.  This is the function the
earlier note read as a voltage: the `0x0B`/`0x05` pair and the `x10000` scaling
are what made it look like a 10 mV/count ADC.

## RSSI / status and the seek path

The seek is a hardware seek with a software timeout, in four pieces.

**Status.**  `FUN_080068E8` reads register `0x0A` (the RSSI/status word) into a
global at `0x20000080`; `FUN_080068D8` returns it.  Two predicates read bits of
that cached word:

* `FUN_08006924` — `word & 0x4000` = **STC** (seek/tune complete)
* `FUN_0800690C` — `word & 0x2000` = **SF/BL** (seek failed / band limit)
* `FUN_0800693C` — register `0x07`'s low nibble = **SNR**[3:0]

RSSI itself (`word & 0xff`) is read but never consumed in this path; only STC
and SF/BL drive the decision.

**Start.**  `FUN_0800D1F8` sets the state flags and calls
`FUN_080069A6` (clear TUNE) then `FUN_08006952` (read register 2, set
SEEK | SEEKUP | SKMODE = `0x0700`).  SEEKUP is always set, so the stock only
ever seeks **up**, and SKMODE = 1 stops at the band edge rather than wrapping.

**Timeout.**  `FUN_0800D410` is a countdown, reached from the periodic tick
`FUN_0801E034` (gated on bit 0 of `0x2001E170`): while a seek is in progress it
decrements the 16-bit counter at state `+6` (initialised to `0xfa` = 250); at
zero it sets state `+5` and reloads.  This is what schedules the completion
poll, not a hardware interrupt — the BK1080's GPIO2 STC interrupt is configured
but not used.

**Completion — `FUN_08017BB4`,** called every pass of the main loop
`FUN_08024448` and gated on state `+1` and `+5`:

```
if state[+1] and state[+5]:
    state[+5] = 0
    freq  = FUN_0800687C()        -- READCHAN + band base
    FUN_080068D8()                -- read reg 0x0a (cached)
    stc   = FUN_08006924()        -- STC
    sfbl  = FUN_0800690C()        -- SF/BL
    FUN_0800693C()                -- SNR (read, not used)
    FUN_08006982()                -- clear SEEK
    delay(5)
    if sfbl == 1 and freq < 7600000:  freq = 7600000
    elif sfbl == 1:                   freq = 6400000
    state[+0xc] = clamp(freq)
    FUN_08019640(); FUN_0800AF4C()    -- display/audio
    FUN_0800D218()                    -- state tick
    FUN_08006F9C(state[+0xc])         -- re-tune to the result
    state[+6] = 0xfa
```

So on success the found channel is re-tuned (the part needs its TUNE re-latched
after a seek), and on failure the radio falls back to 76.0 or 64.0 MHz — the two
band bases, again.

## What the stock's FM feature does

The state struct is at `0x20003EDC` and is shared by all of the above:

| offset | meaning | evidence |
|---|---|---|
| `+1` | seek in progress | set by `FUN_0800D1F8`, cleared by `FUN_0800D274`/`FUN_08008944` |
| `+4` | unnamed flag | set by `FUN_0800D1F8`, set to an argument by `FUN_0800D1EC` |
| `+5` | completion poll gate | cleared by `FUN_0800D1F8`/`FUN_08017BB4`, set by `FUN_0800D410` |
| `+6` | seek countdown (16-bit) | `0xfa`, decremented by `FUN_0800D410` |
| `+8` | **FM radio on/off** | toggled by `FUN_0800D318`, applied by `FUN_0800D35C` |
| `+9` | tuning mode (channel list vs manual) | toggled by `FUN_0800D2F8`, read by `FUN_0800D294` |
| `+0xc` | current frequency, 10 Hz units | set by `FUN_0800D35C`/`FUN_08017BB4` |
| `+0x10` | channel-list bitmap | tested by `FUN_0800F13C`, filled from settings |

The feature's shape:

* `FUN_0800D318` toggles state `+8` and calls `FUN_0800D334(0|1)`;
  `FUN_0800D334` sets it and runs `FUN_0800D35C`.
* `FUN_0800D35C` is the apply: **FM off** parks the bus (`PC14` and `PB2` low)
  and restores the audio path; **FM on** loads the stored frequency
  (`FUN_0800F440`), writes the 68-byte init block (`FUN_08007124`), tunes
  (`FUN_08006F9C`) and sets up the audio path.
* `FUN_0800D2F8` flips `+9` and retunes; `FUN_0800D294` steps the frequency
  (channel list via `FUN_08008BB4`, which walks the `+0x10` bitmap, or a fixed
  step via `FUN_08008C0C`) and retunes.
* `FUN_0800D218` is the mode tick: with `+1 == 0` and `+9 != 0` it starts a seek
  (`FUN_0800D1F8`); with `+1 != 0` it calls `FUN_0800D274`, which ends the seek.
* `FUN_08008944` turns FM off when the radio enters a mode that needs the RF
  path back.

The UI strings `FM RADIO` (`0x08026C80`), `FM Radio` (`0x080270D4`), `SeeK...`
(`0x08026960`) and `Seeked!` (`0x080268C0`) are in the image's text tables, so
the feature has a menu entry and seek display.  The exact display routine that
consumes the `Seeked!`/`SeeK...` pointers is not traced (the text tables are
indexed by the UI framework, not by an FM-specific call site).

## The driver

Three files on branch `driver/bk1080`, all unvalidated on the radio:

| file | what it is |
|---|---|
| `firmware/App/driver/i2c_bus.c` / `.h` | the bit-banged I2C wire: start/stop, a byte out with the ACK poll, a byte in, the master ACK, and a settable edge delay.  Pins are `BK1080_SCL_PIN`/`BK1080_SDA_PIN` in `board_pins.h` |
| `firmware/App/driver/bk1080.c` / `.h` | the BK1080 register layer: framing, the 68-byte init block and the register-0x32 writes, the tune, the frequency readback, the status/seek helpers |
| `firmware/tools/test_bk1080.c` | a host test with the bus replaced by a recording stub |

The transport is a separate file for the same reason `rf_bus.c` is: it keeps the
register layer free of any device header, so the host test can replace the wire
and check the exact bytes the part will see.  `bk1080.c` includes only
`i2c_bus.h` (stdlib types), so it compiles on a PC.

### The host test

```sh
cd firmware && gcc -std=c11 -I App -I App/driver tools/test_bk1080.c \
    App/driver/bk1080.c -o /tmp/test_bk1080 && /tmp/test_bk1080
```

59 checks, no radio: the fixed device id and `(reg << 1) | R/W` control words,
high-byte-first words, ACK-then-NACK on a read, the 68-byte block byte for byte,
the two register-0x32 writes, the tune at 100.0/87.5/70.0 MHz, the readback
arithmetic for all three band bases, and the STC/SF-BL/RSSI/SNR fields and the
seek read-modify-writes.  It proves we *ask* correctly; it cannot tell whether
the part answers.

### What is deliberately not in the driver

Only what the evidence supports: no FM audio routing, no application state
machine, no `0x32` field semantics (the values are replayed verbatim), and no
identity check pretending the stock does one.  `bk1080_read_id()` reads the
datasheet chip id for a caller that wants a liveness probe, and says so.

## What is ruled out

| ruled out | evidence |
|---|---|
| a companion battery gauge | no gauge in the teardown; every register read on the bus is a BK1080 register |
| `0x0B` is RSSI | datasheet table 11: `0x0B` = Read Channel, `0x0A` = RSSI status |
| the offsets are a divider zero point | they are the datasheet BAND bases 87.5/76.0/64.0 MHz, and `(x+base)*10000` is the FM frequency |
| `FUN_08006F9C` is a voltage write-back | its register-5/register-3 arithmetic is the tune, and it matches the datasheet's channel formula exactly |
| the stock checks an identity | `FUN_08007158` is only ever called with registers `0x02/0x03/0x05/0x07/0x0A/0x0B`; register 1 is never read |
| the seek uses the STC interrupt | the BK1080's GPIO2/STCIEN bits are configured, but completion is polled after a 250-tick countdown |

## Open

1. **The bus has not been exercised on the radio.**  The pins, framing and
   register accesses are read out of the stock image; no ACK has been observed
   from this part here.  A logic-analyser capture while the stock displays
   voltage/frequency is the missing measurement (`ra89r_battery.md` reaches the
   same conclusion from its side).
2. **The 68-byte block's fields** are only partly named (registers 1, 2, 5).
   The rest, and the read-only registers it writes, are recorded as a vendor
   blob.
3. **Register `0x32`** is outside the public map and its two values are
   unexplained.
4. **The seek timeout's real duration** depends on the tick that sets
   `0x2001E170` bit 0; the countdown is 250 ticks, but the tick rate has not
   been measured.
5. **The FM audio path**: the stock's `FUN_0800D35C`/`FUN_08016200`/`FUN_0800AF4C`
   calls set the audio path up when FM turns on; where the BK1080's `LOUT`/`ROUT`
   land on this board is not traced.
6. **The exact UI** that consumes the `SeeK...`/`Seeked!`/`FM RADIO` strings.
