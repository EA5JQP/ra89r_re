# BK4829 RF transceiver

**Status: identified, its boot configuration extracted, and a driver written —
branch `driver/bk4829`.  The bus and both identity reads are validated on the
radio; the register configuration is accepted by both parts, but its RF effect
has not been observed yet.**

The radio carries **two** BK481x transceivers.  This is the one on chip select
`PB8`; its sibling is the BK4815 on `PB13` (`ra89r_bk4815.md`).  The bus they
share, the boot bring-up order and the power path are in `ra89r_rfpath.md`.

## Identity and wiring

| | |
|---|---|
| chip select | `PB8` — GPIOB mask `0x100`, active low |
| clock | `PA12` (shared with the BK4815) |
| data | `PB12` (shared, bidirectional: driven to send, released to read) |
| register 0 | reads **`0x4829`** |

**Both parts identify themselves in register 0, and that is the whole of the
stock's identity check** — there is no separate version register anywhere in the
image.  A BK4829 read of register 0 must return `0x4829` and a BK4815 read of
register 0 must return `0x4816`; that is what the bring-up fw's `R` command
turns into a pass/fail, and it is the cheapest possible proof that the bus, the
select and the part are all alive.

Register 0 is also *written* (the stock writes `0x8000` then `0x0000` as its
first two boot writes, which reads as a reset), so reading it back after a
configuration is a meaningful check rather than a constant.

The stock never reads anything else for identification.  The other registers it
does read, which the console probe uses as a second liveness sample, are
`0x0b`/`0x0c`/`0x0d`/`0x0e`, `0x31`, `0x33`, `0x40`, `0x51`, `0x63`/`0x64`/
`0x65`/`0x67`/`0x68`/`0x69`/`0x6a` on this chip, and `0x0b`, `0x28`, `0x43`,
`0x44`, `0x73`, `0x75` on the BK4815.

`FUN_08009772` is the stock's own identity check: it is one call to
`FUN_080180F0(0)` — this chip's read of register 0 — compared against `0x4829`.
On failure `FUN_08006B78` calls `FUN_08015D14(0x0b)` and returns without
configuring the chip.

Framing: `reg & 0x7f` to write, `reg | 0x80` to read, then one 16-bit word MSB
first.  The register layer is `FUN_080220A0(value, reg)` for writes and
`FUN_080180F0(reg)` for reads; both bracket the transfer with `PB8` low, and the
bits go out through `FUN_08017D6C`/`FUN_08017FE4` on `PA12`/`PB12`
(`ra89r_rfpath.md` has the timing and the direction switching).  The **first**
argument of `FUN_080220A0` is the value and the **second** is the register; it
byte-swaps the 16-bit value into a two-byte buffer and passes it to the write
core `FUN_08021FF4(buf, reg, len)`, which is what makes the word go out MSB
first.

## The boot configuration — `FUN_08006B78`, 39 registers in 40 writes

```
reg 00 = 0x8000    reg 2f = 0x9890    reg 48 = 0xb386
reg 00 = 0x0000    reg 3a = 0x9a7c    reg 49 = 0x2a32
reg 37 = 0x9d1f    reg 3e = 0x94c6    reg 4a = 0x5430
reg 13 = 0x03df    reg 3f = 0x07fe    reg 4d = 0xa015
reg 12 = 0x03db    reg 40 = 0x34f0    reg 4e = 0x6f10
reg 11 = 0x033a    reg 46 = 0x6050    reg 4f = 0x2a28
reg 10 = 0x0318                       reg 53 = 0x2028
reg 14 = 0x0210                       reg 73 = 0x6681
reg 19 = 0x1041                       reg 77 = 0x88ef
reg 1c = 0x0422                       reg 7b = 0x73dc
reg 1d = 0x2aab                       reg 7d = 0xe920  [overwritten below]
reg 1e = 0x4c58                       reg 7e = 0x303e
reg 1f = 0x165a                       reg 4c = 0xe520
reg 25 = 0x6dba    -- then FUN_0801BAF4() is called --
reg 28 = 0x0b40                       reg 48 = 0xb3b5   (rewritten)
reg 29 = 0xaa00                       reg 47 = 0x6042   (last write)
reg 2a = 0x6600
reg 2c = 0x0022
```

Order matters: the first two writes go to register 0 (`0x8000` then `0x0000`),
the middle block runs in the order shown, and the last two (`0x48`, `0x47`) come
after `FUN_0801BAF4`.  The body is 37 explicit `FUN_080220A0` calls plus the two
at the end, i.e. **40 write transactions over 39 distinct registers** — `0x7d` is
written twice, and the second write is the one that sticks (below).

**`FUN_0801BAF4` always overwrites register `0x7d`.**  It reads a small field at
`0x20009f37` and a flag at `0x20000301`, and every one of its four branches ends
at the same `FUN_080220A0(0xe940 | v, 0x7d)`:

| `0x20000301` | field < 3 | field ≥ 3 |
|---|---|---|
| `== 1` | `v = (3 - field) * 3 + 0x0c` | `v = (field - 3) * 3 + 0x0c` |
| `!= 1` | `v = (3 - field) * 4 + 0x18` | `v = (field - 3) * 4 + 0x18` |

So the `0xe920` the sequence writes explicitly two calls earlier is **dead**: the
value that reaches the chip is always `0xe940 | v`, i.e. somewhere in
`0xe943`…`0xe960` for a field of 0…5 (`0xe943`, `0xe946`, `0xe949`, `0xe94c`,
`0xe94f`, `0xe952` when the flag is 1; `0xe94c`…`0xe960` when it is not).
`0xe920` is not of that form at all
(`0xe940` sets bit 6; `0xe920` sets bit 5 and clears bit 6), so an earlier reading
of this sequence as "this image writes `0xe920`" was wrong — a correction worth
keeping, because it is exactly the sort of off-by-one register write that makes a
bring-up look configured while the part is not.

The field is the byte at `0x20009F28 + 0x0f`, from the same runtime configuration
struct whose `+0x1c` byte selects the display language (`ra89r_rfpath.md`); the
flag is the same one `FUN_08016788` tests before calling `FUN_080139E4`, and
`FUN_0800DCAC` clears it to `0`.  Neither is a constant in the code, so the value
this radio actually sends at boot had to be traced through the codeplug rather
than read off the listing — which is done below.

Where those inputs come from, and what this radio actually sends.  The field
(`0x20009F28 + 0x0f`) has exactly **one** writer, `FUN_0800FE18` at `0x0800FFB4`,
storing `buffer[10] & 7`; that function reads 32 bytes from the external flash
address held in `*(u32 *)0x08025FF8` into a buffer at `sp + 4`, and the same
record byte's bits 4–5 go to `+0x10`.  The address resolves to **`0x2020`** in the
EEPROM, and in this radio's dump byte 10 of that block is `0x03` — so **field =
3**, the first value of the `field >= 3` group, i.e. the middle of the ladder.

The flag has the opposite story: the whole image contains exactly one instruction
that writes `0x20000301` — `0x0800DD4A`, inside `FUN_0800DCAC` — and it writes
**0**; every other reference reads it.  Nothing copies a block over it either (the
address is never used as a copy destination), so the `flag == 1` row of the table
never applies on this hardware and the `flag != 1` row is the live one.  That also
means `FUN_08016788` never calls `FUN_080139E4`.

With field 3 and the flag clear:

```
v = (field - 3) * 4 + 0x18 = 0x18      ->      reg 0x7d = 0xe940 | 0x18 = 0xE958
```

**So the image's own value for `0x7d` is `0xE958`** — not `0xE920`, and not
`0xE940`.  The field itself is still unnamed (it is a three-bit codeplug setting,
and a power level is the obvious candidate given the six-step ladder), so
`firmware/App/driver/bk4829.c` writes the derived constant rather than computing
it.

This one had a suggested check that the radio has now ruled out, which is worth
keeping rather than deleting: "read `0x7d` back after a stock boot" cannot be
done, because entering update mode resets both parts and they come up at their
defaults — `0x7d` reads `0xE51C` on a fresh chip, a value no writer in the image
can produce (see "Validated on the radio" below).  The derivation therefore
stands on the codeplug and the decompiler alone, and is unverified against a
running stock radio by construction.

nearer the K1's **BK4819** constant `0xE940` than its BK4829 one — so the K1 files
disagree about this register for a reason, and this board's own answer is the
computed value, not either literal.

## The driver

Three files on branch `driver/bk4829`, all unvalidated on the radio:

| file | what it is |
|---|---|
| `firmware/App/driver/rf_bus.c` / `.h` | the shared 3-wire bus: select is a parameter, so one bit layer drives both parts |
| `firmware/App/driver/bk4829.c` / `.h` | this chip's framing (`reg \| 0x80` / `reg & 0x7f`) and the 39-register boot table |
| `firmware/App/driver/bk4815.c` / `.h` | the sibling's framing (`(reg & 0x7f) << 1` with the read flag in bit 0), its 36-byte block and its 33 writes |

The bus was split out of the BK4829 driver because the two register layers
genuinely differ; keeping the framing separate is what stops a copy-paste between
them from looking right.  `rf_bus.c` follows the stock's phases rather than a
guess — a byte goes out with the data set while the clock is low and the rising
edge latching it, while 16 bits are sampled **while the clock is low** and then
the clock rises (`FUN_08017D6C` / `FUN_08017FE4`).

The table is a transcription of the stock's write *calls*, with one deliberate
departure: `0x7d` carries the derived `0xe958` rather than the dead literal
`0xe920` the stock writes and immediately overwrites (above).  The entry says so
in a comment.

### Two initialisation paths, and why both exist

`bk4829_configure()` replays the **stock** boot configuration extracted from this
radio's own image, and is what `W`/`X` exercise.  `bk4819.c` (the K1-compatible
layer, bound to this part) has its own `BK4819_Init()`, which replays the
**F4HWN UV-K1/K5V3 build's** sequence for the same part family, and is what the
port needs.  They are different tables for the same chip: the stock's is
evidence, the K1's is the interface the ported application will call, and having
both makes it easy to compare them on the radio -- `K` runs the K1 path, `W` the
stock one.  The K1 path is also the first thing here that can make the radio
receive: `K` inits, tunes 145.7500 MHz into the same `0x38`/`0x39` pair the stock
uses (raw 10 Hz units -- F4HWN's `FUN_0800F670`-equivalent is a stub that returns
its argument), sets AF and turns RX on.

### The bring-up test

Two ways to run it, and they check different halves:

* **On the radio, `R`**: probes both ids and then reads a second register from
  each (`0x63`/`0x67` on this chip, `0x73` on the BK4815 — registers the stock
  reads too), so "answers its id and nothing else" is visible rather than assumed
  fine.  `W` replays both boot configurations, re-probes, and prints register
  `0x7d` read back for comparison with `0xE958`.
* **On a PC, `firmware/tools/test_rf.c`**: runs the two register layers against a
  recording bus stub and asserts the exact bytes each part will see — the
  identity handshake, both address encodings, the 36-byte block against the image
  byte for byte, and `0x7d` = `0xE958`.  30 checks, no radio:

```sh
cd firmware && gcc -std=c11 -I App -I App/driver tools/test_rf.c \
    App/driver/bk4829.c App/driver/bk4815.c -o /tmp/test_rf && /tmp/test_rf
```

### Validated on the radio

`R` on a freshly booted radio, before any write, returns exactly what the part
should be:

```
RF bus: PA12 clock, PB12 data, PB8 = BK4829, PB13 = BK4815
  BK4829 reg 0x00 = 0x4829  (expected 0x4829) -- present
  BK4815 reg 0x00 = 0x4816  (expected 0x4816) -- present
```

So the shared clock and data lines, both chip selects and **both address
encodings** work on hardware — that is the whole of the transport, and it is the
first thing on this branch that is not a static reading.

`W` then sent both boot configurations (39 writes; 1 block + 33 writes) and both
parts still answered their own id afterwards, so the sequencing does not leave
either part deaf.  `X`, which reads every register the configuration wrote back
and compares, reports **36 of 36 landed on the BK4829** and **31 of 33 on the
BK4815** — the two exceptions are described below and are the chip's behaviour,
not a transcription error.

### A fresh chip reads back its power-on defaults, not the stock's state

The obvious next experiment — boot the stock firmware, then read the registers
with this one — does not work, and the second hardware run proved it rather than
leaving it as an assumption.  A read-only dump of a freshly booted radio gave:

| part | register dump |
|---|---|
| BK4829 | `21=06D8 24=8C5E 30=0000 33=FF00 47=6140 7D=E51C 63=00FF 67=0000` |
| BK4815 | `0C=FFFF 75=0400 73=8001 4C=64A4 55=70A6 62=0003` |

**These are the parts' defaults.**  The decisive one is the BK4815's `0x0C`: it
reads `0xFFFF`, while the stock's boot init always writes `0x0A03` to it (the last
of its 33 writes) and our own write to that register reads back correctly after
`W`.  A register the stock always configures cannot read `0xFFFF` on a
stock-configured chip, so nothing had configured these parts: getting this
firmware into flash means entering update mode, and the parts come up reset.
Reading the stock's live configuration this way is therefore **structurally
impossible**, not merely untried.

Two of the defaults are worth a second look because they coincide with stock
constants: `0x21 = 0x06D8` is exactly what `FUN_0801740C` writes there, and
`0x47 = 0x6140` is what `FUN_08017628(1)` writes.  That is consistent with the
vendor's init writing known-good values that happen to be the defaults — it is
*not* evidence that the stock had run.

**Consequence for register `0x7d`.**  The dump reads `0xE51C`, and the image
cannot produce that value: this chip has exactly two writers of `0x7d`
(`FUN_08006B78` writes `0xE920`, `FUN_0801BAF4` writes `0xE940 | v`), and there
are **no block writes** to this part at all — the write core `FUN_08021FF4` takes
a length, but its only caller in the whole image is the two-byte wrapper
`FUN_080220A0`.  So `0xE51C` is a default, and the derived `0xE958` remains a
derivation: the read-back after `W` shows the register took *our* value, which is
a real result about the bus, but it says nothing about the stock's.

The three BK4815 placeholder registers (`0x4c`, `0x55`, `0x62`) are in the same
position, and their defaults are now recorded above.  They come from the stock's
own RAM (`0x2000449a`/`9c`/`9e`), so recovering them means tracing what fills that
RAM — and `0x2000449E` has a known source already: `FUN_0800DCAC` stores a
two-bit codeplug field there.

### The two BK4815 registers that do not store what is written

Neither ever reads back what is written, and across runs their read values
*change*, so they are not simply bits that fail to store:

```
    0x44:  wrote 0x8000, read 0x8010 / 0x8111 / 0x0000 (unconfigured)
    0x49:  wrote 0x1a02, read 0x1602 / 0x1882 / 0x0002 / 0x000d (unconfigured)
```

Bit 4 of `0x44` reads 1 whatever is written and `0x49` loses at least bit 10 —
but the varying high bits say more: these two registers carry **status** bits the
part updates on its own.  An earlier version of this note called them fixed bits;
the extra runs are what showed that was too strong.  Both are written with the
stock's own values here, so it is a property of the part rather than a
transcription error, and it is why a strict write-then-read comparison flags
exactly these two and nothing else, every time.

Everything else the configuration carries stores and returns exactly what was
sent — including, once `X` learned to check it, all 18 words of the 36-byte block
written to registers 2..19 in one select pulse (`BK4815 block: 18 registers
compared, 0 differ`).  Both framings, the single write and the block write are
verified on hardware.

### The K1-compatible path, on the radio

`K` (the ported F4HWN interface: `BK4819_Init`, tune 145.7500 MHz, AF on, RX on)
was the thing that finally moved something.  It reported

```
RF: K1-compatible bring-up done (id 0x4829)
  frequency 145.7500 MHz -> reg 0x38 = 0x6598, 0x39 = 0x00de
  (expect 0x6598 / 0x00DE; reg 0x67 RSSI = 0x009a)
```

Two results in that.  The frequency path is exact — `0x38`/`0x39` hold the
split 10 Hz word, the same pair and the same encoding the stock's `FUN_08017158`
uses.  And **`0x67` moved off zero**: an unconfigured part read `0x0000`, and
after the K1 init and `RX_TurnOn` it reads `0x009A`, then `0x009E` a moment later.
That is the first RF-observable effect this branch has produced.

Those readings sat below both of the stock's squelch marks (`0xB4` = 180,
`0xCF` = 207), which is what "no signal present" looks like — so at that point the
receive path was producing plausible numbers but had not been shown to *respond* to
anything.

**It does respond.**  With a carrier keyed near 145.7500 MHz the same command
reads

```
  K, carrier on:   reg 0x67 = 0x00EC   (236)   -- identical across three presses
  K, carrier off:  reg 0x67 = 0x0039   ( 57)
```

236 is stable across three presses that each reset and re-initialise the part, and
it sits **above** `0xCF`, the level at which the stock's own squelch routine opens;
57 sits below `0xB4`, where it closes.  The two readings straddle the stock's own
decision threshold, which is the strongest form this evidence takes without a
scope on the part: the receive path tracks a carrier.

`S` (added for this) samples `0x67` every 200 ms for 4 s and prints each value
against those two marks, so a carrier-on and carrier-off pair can be compared as
numbers rather than argued from single readings — which the wander described below
made necessary.

`R` after `K` also shows the K1 table's values in the part — `33=9000`,
`47=6142`, `30=bff1` — which is the port's writes landing, confirmed by a second
route: `X` read `0x37 = 0x9F1F`, and that is exactly what `BK4819_RX_TurnOn`
writes over `BK4819_Init`'s `0x9D1F`.  The port's internal ordering is behaving as
the K1 intends.

**A correction `X` earned.**  Its first version compared the stock table against
whatever the chip happened to hold, so running it after `K` reported 19 of 36
"differences" on this part and 29 of 33 on the BK4815 — the BK4829's were the
K1's own values and the BK4815's were power-on defaults, because `K` touches only
the BK4829.  Those numbers were history, not faults.  `X` now writes every
register before reading it back and covers the BK4815's block too, and the next
run came back clean:

```
  BK4829: 36 registers compared, 0 differ  -- every write landed
  BK4815: 33 registers compared, 2 differ   (see ra89r_bk4815.md)
  BK4815 block: 18 registers compared, 0 differ
```

So the whole configuration path is verified on hardware: both parts, both
addressing schemes, single writes and the block write.  The `R` taken straight
after that `X` is its own confirmation of what landed — the BK4829 reads
`47 = 0x6042` and **`7d = 0xE958`**, i.e. the stock table's values, and `0xE958`
is the derived constant holding in the register for the first time (still no
evidence that the *stock* sends it, but it does survive a write and a read).

**What the runs also show moving.**  Before the carrier test, RSSI wandered between
`0x0039` and `0x009D` across runs, where an unconfigured part sat at `0`.  All of
those are below the stock's own squelch marks, so they were a live noise floor with
AGC settling rather than a signal — consistent with the carrier test above, which
pushed the same register to `0xEC` when a signal was actually present.  `0x0C` on
the BK4815 was observed going from the written `0x0A03` to `0x0603` on its own
between two commands, so that register carries a self-clearing bit.

With the carrier result in hand the merge rule was met, and `driver/bk4829` is
merged into `develop`.

The PC test proves we *ask* correctly; `R` on the radio proved the parts answer.

## Other configuration in the same image

The boot init is not the whole story; the per-band, mode and RX/TX setup live in
other routines.  The decompiler pass turned most of the register names up:

| reg | who touches it | what it is |
|---|---|---|
| `0x33` | `FUN_080137D4(mask, value)`, also `FUN_0800D434` | band/filter select: clears bit `14 - n` for each bit `n` of `mask`, sets bits `0..6` from `value` |
| `0x13` | `FUN_08016228`, `FUN_08009CC4`, `FUN_080052B8` | T/R level (`0x03BE` / `0x03FF`) and the eight-step squelch ramp (`0x3b0 \| (8 - level)` … `0x3ff`) |
| `0x47` | `FUN_08016228`, `FUN_08006B78` | T/R switch — `0x6042`/`0x6142` or `0x6040`/`0x6740` at runtime |
| `0x30`, `0x31` | `FUN_08016228`, `FUN_08009CC4` | `0x30` = `0xBFF1`/`0xBDF1`; `0x31` read-modify-written (bit 2 cleared on entry, set on the way back) |
| `0x63`, `0x65`, `0x67`, `0x99` | read in `FUN_080052B8` | metering; `0x67 & 0x1ff` is the RSSI the UI prints as `RSSI R67 %d` |

So this chip carries the filter, the metering and the T/R set, while the BK4815
carries a band select and a path switch instead (`ra89r_bk4815.md`).  The T/R path
picks between them from the channel frequency — at or below 134 MHz the BK4829
gets the T/R registers, above it the BK4815 gets its `0x0c` — see "What the T/R
flag is" in `ra89r_rfpath.md`.

Ranked by how many registers each writes, the per-band/per-mode routines are
`FUN_0801740C` (18 writes), `FUN_08017280` (7), `FUN_08016DE8` (6),
`FUN_0801754A` (5), `FUN_08018A46` and `FUN_08009CC4` (4 each), `FUN_08016F7C`
and `FUN_08017668`.  What they write, verbatim:

| routine | writes (reg = value, in order) |
|---|---|
| `FUN_0801740C` | **reg `0x09` ×16** — `0x006f`, `0x106b`, `0x2067`, `0x3062`, `0x4050`, `0x5047`, `0x603a`, `0x702c`, `0x8041`, `0x9037`, `0xa025`, `0xb017`, `0xc0e4`, `0xd0cb`, `0xe0b5`, `0xf09f`; then `0x21 = 0x06d8`, `0x24 = (state[0x20000332] << 7) \| 0x807e` |
| `FUN_08017280` | `0x24 = 0`, `0x47 = 0x6142`, `0x37 = 0x9d1f`, `0x50 = 0x3b20`, `0x70 = 0`, `0x30 = 0`, `0x30 = 0xc1fe` |
| `FUN_08016DE8` | `0x32 = 0x244`, `0x24 = 0`, `0x47 = 0x6042`, `0x4a = 0x5450`, `0x4a = 0x5448`, `0x50 = 0x3b20` |
| `FUN_0801754A` | `0x46 = 0xa00a`, `0x79 = 0x6005`, `0x7a = 0x589a`, `0x31 \|= 4`, `0x30 = 0xbdf1` |
| `FUN_08018A46` | `0x37 = 0x9d1f`, `0x30 = 0x200`, `0x30 = 0xbdf1`, `0x30 = 0xbff1` |
| `FUN_08017668` | `0x37 = 0x9d1f`, `0x52 = <table at 0x08017694 + 4>`, `0x30 = 0`, `0x30 = 0xc3fe` |
| `FUN_08016F7C` | `0x07 = <computed>` |

Two of those registers look like they carry a *level* rather than a switch, and
they are the best remaining candidates for wherever the TX-power setting lands:
`0x30` walks a ladder (`0x200`, `0xBDF1`, `0xBFF1`, `0xC1FE`, `0xC3FE`) across
these routines, and `0x31` is read-modify-written with bit 2 as a flag.

The `0x09` block is the clearest one: sixteen values whose high nibble is their
own index `0…0xF` and whose low byte is the coefficient, i.e. a **16-tap filter
RAM** loaded through one register, which fits the `0x33` band/filter select above.
Read as signed bytes the taps are

```
111  107  103   98   80   71   58   44   65   55   37   23  -28  -53  -75  -97
```

— two descending runs of eight, which is worth remembering when the register's
semantics get mapped.

### Register `0x09` is a filter programmer, not a table dump

`FUN_0801740C` is only the fixed variant.  The real entry point is
`FUN_0800B634(n)`, called from the per-mode routine `FUN_08016DE8` as
`FUN_0800B634(channel[0x79] - 1)` — and as `FUN_0800B634(0)` when that byte is 0
and `config[0] == 1` — so **`channel + 0x79` is a filter-bandwidth index** and the
function's branching resolves to three set-ups:

| `channel[0x79]` | path | taps written | `0x21` | `0x24` |
|---|---|---|---|---|
| `1` (or `0` with the config flag) | `FUN_0801740C` | 16, fixed values | `0x06d8` | `(state << 7) \| 0x807e` |
| `2` | `FUN_080174D0(1)` | 2 (indices 0–1) | `0x06fd` | `(state << 7) \| 0x8021` |
| `3` | `FUN_080174D0(0xF)` | 16 (indices 0–0xF) | `0x06fd` | `(state << 7) \| 0x802f` |

any other value of `n` lands on the `FUN_080174D0(1)` path, because the function
only tests for `0` and `2`.

`FUN_080174D0(n)` walks a **RAM** table at `0x200000D0` and passes each entry
through `FUN_0801ACAC(value, index)`, which is soft-float arithmetic — calls into
the double-precision helpers at `0x08004528`/`0x08004344`/`0x08004428` etc., with
a `% 10` rounding step — before OR-ing the index into the high nibble
(`| index << 12`) and writing register `0x09`.  So the stock does not merely dump
a coefficient table: it **designs the channel filter at run time** (a windowed
coefficient set of 2 or 16 taps) and programs it a tap at a time, then selects the
mode through `0x21`/`0x24`.  The RAM table's own origin is open, and so is what
each bandwidth index means in kHz.

Note that `0x4a` and `0x30` are each written twice in a row in `FUN_08016DE8` and
`FUN_08018A46`; as with `0x7d` at boot, only the second value survives, so a table
that keeps only the last write per register is right, and one that keeps the first
is wrong.

`FUN_08017176`, `FUN_08006E6A`, `FUN_0801C564` and the other helpers these
routines call are not identified; the writes above are what reaches this chip.
