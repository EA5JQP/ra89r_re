# BK4829 RF transceiver

**Status: identified, its boot configuration extracted, and a driver written —
branch `driver/bk4829`, committed but not yet validated on the radio.**

The radio carries **two** BK481x transceivers.  This is the one on chip select
`PB8`; its sibling is the BK4815 on `PB13` (`ra89r_bk4815.md`).  The bus they
share, the boot bring-up order and the power path are in `ra89r_rfpath.md`.

## Identity and wiring

| | |
|---|---|
| chip select | `PB8` — GPIOB mask `0x100`, active low |
| clock | `PA12` (shared with the BK4815) |
| data | `PB12` (shared, bidirectional: driven to send, released to read) |
| register 0 | reads **`0x4829`** |

`FUN_08009772` is the stock's own identity check: it is one call to
`FUN_080180F0(0)` — this chip's read of register 0 — compared against `0x4829`.
On failure `FUN_08006B78` calls `FUN_08015D14(0x0b)` and returns without
configuring the chip.

Framing: `reg & 0x7f` to write, `reg | 0x80` to read, then one 16-bit word MSB
first.  The register layer is `FUN_080220A0(value, reg)` for writes and
`FUN_080180F0(reg)` for reads; both bracket the transfer with `PB8` low, and the
bits go out through `FUN_08017D6C`/`FUN_08017FE4` on `PA12`/`PB12`
(`ra89r_rfpath.md` has the timing and the direction switching).  The **first**
argument of `FUN_080220A0` is the value and the **second** is the register; it
byte-swaps the 16-bit value into a two-byte buffer and passes it to the write
core `FUN_08021FF4(buf, reg, len)`, which is what makes the word go out MSB
first.

## The boot configuration — `FUN_08006B78`, 39 registers in 40 writes

```
reg 00 = 0x8000    reg 2f = 0x9890    reg 48 = 0xb386
reg 00 = 0x0000    reg 3a = 0x9a7c    reg 49 = 0x2a32
reg 37 = 0x9d1f    reg 3e = 0x94c6    reg 4a = 0x5430
reg 13 = 0x03df    reg 3f = 0x07fe    reg 4d = 0xa015
reg 12 = 0x03db    reg 40 = 0x34f0    reg 4e = 0x6f10
reg 11 = 0x033a    reg 46 = 0x6050    reg 4f = 0x2a28
reg 10 = 0x0318                       reg 53 = 0x2028
reg 14 = 0x0210                       reg 73 = 0x6681
reg 19 = 0x1041                       reg 77 = 0x88ef
reg 1c = 0x0422                       reg 7b = 0x73dc
reg 1d = 0x2aab                       reg 7d = 0xe920  [overwritten below]
reg 1e = 0x4c58                       reg 7e = 0x303e
reg 1f = 0x165a                       reg 4c = 0xe520
reg 25 = 0x6dba    -- then FUN_0801BAF4() is called --
reg 28 = 0x0b40                       reg 48 = 0xb3b5   (rewritten)
reg 29 = 0xaa00                       reg 47 = 0x6042   (last write)
reg 2a = 0x6600
reg 2c = 0x0022
```

Order matters: the first two writes go to register 0 (`0x8000` then `0x0000`),
the middle block runs in the order shown, and the last two (`0x48`, `0x47`) come
after `FUN_0801BAF4`.  The body is 37 explicit `FUN_080220A0` calls plus the two
at the end, i.e. **40 write transactions over 39 distinct registers** — `0x7d` is
written twice, and the second write is the one that sticks (below).

**`FUN_0801BAF4` always overwrites register `0x7d`.**  It reads a small field at
`0x20009f37` and a flag at `0x20000301`, and every one of its four branches ends
at the same `FUN_080220A0(0xe940 | v, 0x7d)`:

| `0x20000301` | field < 3 | field ≥ 3 |
|---|---|---|
| `== 1` | `v = (3 - field) * 3 + 0x0c` | `v = (field - 3) * 3 + 0x0c` |
| `!= 1` | `v = (3 - field) * 4 + 0x18` | `v = (field - 3) * 4 + 0x18` |

So the `0xe920` the sequence writes explicitly two calls earlier is **dead**: the
value that reaches the chip is always `0xe940 | v`, i.e. somewhere in
`0xe943`…`0xe960` for a field of 0…5 (`0xe943`, `0xe946`, `0xe949`, `0xe94c`,
`0xe94f`, `0xe952` when the flag is 1; `0xe94c`…`0xe960` when it is not).
`0xe920` is not of that form at all
(`0xe940` sets bit 6; `0xe920` sets bit 5 and clears bit 6), so an earlier reading
of this sequence as "this image writes `0xe920`" was wrong — a correction worth
keeping, because it is exactly the sort of off-by-one register write that makes a
bring-up look configured while the part is not.

The field is the byte at `0x20009F28 + 0x0f`, from the same runtime configuration
struct whose `+0x1c` byte selects the display language (`ra89r_rfpath.md`); the
flag is the same one `FUN_08016788` tests before calling `FUN_080139E4`, and
`FUN_0800DCAC` clears it to `0`.  Neither is a constant in the image, so the
value this radio actually sends at boot has to be read on the device (or from the
codeplug), not from the listing.  `firmware/App/driver/bk4829.c` therefore carries
`0xe920` as the stock's *literal* pre-tweak write and flags the overwrite in a
comment; the OR operand is unresolved.

Where those inputs come from: `0x20009F28 + 0x0f` has exactly **one** writer,
`FUN_0800FE18` at `0x0800FFB4`, and it stores `(record_byte & 7)` — a **three-bit
codeplug setting**, with the neighbouring two bits of the same record byte
(`>> 4 & 3`) going to `+0x10`.  So register `0x7d`'s operand is a user/CPS
setting rather than a board strap, and a power level is the obvious candidate: the
ladder the formula produces has about six steps, which matches a multi-step power
menu rather than the two `Power 5W`/`Power 10W` strings.  Naming it needs the
codeplug field, not more disassembly.

## How this differs from the UV-K1/K5V3 driver

The K1 tree has both `bk4819.c` and `bk4829.c`, and its own two inits differ:

| reg | K1 `bk4819.c` | K1 `bk4829.c` |
|---|---|---|
| `0x37` | `0x1D0F` | `0x9D1F` |
| `0x7D` | `0xE940` | `0xE920` |
| `0x1F` | `0x5454` | `0xC65A` |
| `0x3E` | `0xA037` | `0x94C6` |

and the K1's BK4829 init carries a block the BK4819's does not: `0x1C`, `0x1D`,
`0x1E`, `0x73`, `0x77`, `0x28`, `0x29`, `0x2A`, `0x2C`, `0x2F`, `0x53`, `0x7E`,
`0x46`, `0x4A`, `0x07`.

This radio's BK4829 against the K1's BK4829 — same chip, two boards.  Identical:
`0x00` ×2, `0x10`–`0x14`, `0x19`, `0x1E`, `0x28`, `0x29`, `0x2A`, `0x2F`, `0x37`,
`0x3E`, `0x4A`, `0x53`, `0x77`, `0x7B`, `0x7D`, `0x7E`.  Different:

| reg | this radio | K1 |
|---|---|---|
| `0x1C` | `0x0422` | `0x07C0` |
| `0x1D` | `0x2AAB` | `0xE555` |
| `0x1F` | `0x165A` | `0xC65A` |
| `0x2C` | `0x0022` | `0x1822` |
| `0x3F` | `0x07FE` | `0x0000` |
| `0x40` | `0x34F0` | `0x3516` |
| `0x46` | `0x6050` | `0x600A` |
| `0x48` | `0xB386` → `0xB3B5` | `0x33A8` |
| `0x49` | `0x2A32` | `0x2AB2` |
| `0x73` | `0x6681` | `0x4691` |

This radio also writes seven registers the K1's init never touches: `0x25`,
`0x3A`, `0x4C`, `0x4D`, `0x4E`, `0x4F`, `0x47`; and the K1 writes `0x36` where
this radio writes `0x2C`.

One caveat on the "identical" list above: `0x7D` matches the K1's BK4829 only as
the *literal* pre-tweak value `0xE920`.  Because this radio's stock always finishes
the init by overwriting `0x7D` with `0xE940 | v`, what this radio actually sends is
nearer the K1's **BK4819** constant `0xE940` than its BK4829 one — so the K1 files
disagree about this register for a reason, and this board's own answer is the
computed value, not either literal.

## The driver

`firmware/App/driver/bk4829.c` / `.h` on branch `driver/bk4829`, modelled on the
K1's driver layout with this board's pins.  It carries the 39 register values
above as a table and exposes `bk4829_init`, `bk4829_detect`, `bk4829_read_reg`,
`bk4829_write_reg`, `bk4829_configure`.  The console gains `R` (read the id — the
stock's own check) and `W` (replay the configuration and re-read the id, so a
silent bus and a configured chip look different).

The table is a transcription of the stock's write *calls*, so `0x7d` appears once
with the stock's literal `0xe920`.  Because the stock then overwrites it (above),
the driver carries a comment at that entry; once the bus answers on the radio, the
last write to `0x7d` is the first thing to check against the stock's value.

Not validated on the radio: `R` has not been run and `W` has not been exercised,
so the branch stays unmerged.

## Other configuration in the same image

The boot init is not the whole story; the per-band, mode and RX/TX setup live in
other routines.  The decompiler pass turned most of the register names up:

| reg | who touches it | what it is |
|---|---|---|
| `0x33` | `FUN_080137D4(mask, value)`, also `FUN_0800D434` | band/filter select: clears bit `14 - n` for each bit `n` of `mask`, sets bits `0..6` from `value` |
| `0x13` | `FUN_08016228`, `FUN_08009CC4`, `FUN_080052B8` | T/R level (`0x03BE` / `0x03FF`) and the eight-step squelch ramp (`0x3b0 \| (8 - level)` … `0x3ff`) |
| `0x47` | `FUN_08016228`, `FUN_08006B78` | T/R switch — `0x6042`/`0x6142` or `0x6040`/`0x6740` at runtime |
| `0x30`, `0x31` | `FUN_08016228`, `FUN_08009CC4` | `0x30` = `0xBFF1`/`0xBDF1`; `0x31` read-modify-written (bit 2 cleared on entry, set on the way back) |
| `0x63`, `0x65`, `0x67`, `0x99` | read in `FUN_080052B8` | metering; `0x67 & 0x1ff` is the RSSI the UI prints as `RSSI R67 %d` |

So this chip carries the filter, the metering and the T/R set, while the BK4815
carries a band select and a path switch instead (`ra89r_bk4815.md`).  The T/R path
picks between them from the channel frequency — at or below 134 MHz the BK4829
gets the T/R registers, above it the BK4815 gets its `0x0c` — see "What the T/R
flag is" in `ra89r_rfpath.md`.

Ranked by how many registers each writes, the remaining per-band/mode routines
are `FUN_0801740C` (18 writes), `FUN_08017280` (7), `FUN_08016DE8` (6),
`FUN_0801754A` (5), `FUN_08018A46` and `FUN_08009CC4` (4 each), `FUN_08016F7C`
and `FUN_08017668`.
