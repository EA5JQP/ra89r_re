# BK4815 RF transceiver

**Status: identified and its boot configuration extracted from the stock image;
no driver yet — the firmware only drives its sibling so far.**

The radio carries **two** BK481x transceivers.  This is the one on chip select
`PB13`; its sibling is the BK4829 on `PB8` (`ra89r_bk4829.md`).  The bus they
share, the boot bring-up order and the power path are in `ra89r_rfpath.md`.

## Identity and wiring

| | |
|---|---|
| chip select | `PB13` — GPIOB mask `0x2000`, active low |
| clock | `PA12` (shared with the BK4829) |
| data | `PB12` (shared, bidirectional) |
| register 0 | reads **`0x4816`** |

`FUN_08009758` is the stock's identity check: it is one call to
`FUN_08018060(0)` — this chip's read of register 0 — compared against `0x4816`.
On failure `FUN_08006A0C` calls `FUN_08015D14(0x0b)` and returns without
configuring the chip.  (Both chips' inits pass the **same** error code, which is
why the two error strings cannot simply be split one per chip — see
`ra89r_rfpath.md`.)

**Its framing differs from the BK4829's.**  This chip is addressed with
`(reg & 0x7f) << 1` to write and `((reg & 0x7f) << 1) | 1` to read — the
address byte carries the register shifted left, with bit 0 as the read flag —
whereas the BK4829 puts the read flag in bit 7 and sends the register unshifted.
The register layer is `FUN_08022082(value, reg)` for writes and
`FUN_08018060(reg)` for reads, wrapping `FUN_08021F78` on the shared
`PA12`/`PB12` bit layer (`ra89r_rfpath.md`).

`FUN_08021F78(buf, reg, len)` writes `len` bytes starting at one register
address, so a whole block goes out under a single select pulse — which is how the
stock loads this chip's 18-register table (below).

## The boot configuration — `FUN_08006A0C`, 33 writes plus an 18-register table

```
FUN_08021F78(0x08024E40, reg 2, 0x24)   -- 36 bytes = 18 registers, see below
reg 70 = 0xa000    reg 4b = 0xf606    reg 6a = 0xcc31
reg 28 = 0x8820    reg 4c = <RAM>     reg 6b = 0x3415
reg 29 = 0x2050    reg 54 = 0xfc46    reg 6c = 0xe927
reg 2c = 0x8a2f    reg 55 = <RAM>     reg 6d = 0x6618
reg 2d = 0x1bc0    reg 58 = 0x0208    reg 7a = 0x46a3
reg 40 = 0x8000    reg 59 = 0xf7a1    reg 7b = 0x0002
reg 41 = 0xe000    reg 5e = 0x8028    reg 7c = 0xf3ac
reg 44 = 0x8000    reg 62 = <RAM>     reg 7d = 0x76b5
reg 45 = 0x67ff    reg 67 = 0xc31f    reg 7e = 0xfff5
reg 47 = 0x0a18    reg 68 = 0x4020    reg 7f = 0x3568
reg 48 = 0xa002                       reg 0c = 0x0a03
reg 49 = 0x1a02
```

Three writes take their value from RAM rather than a constant — registers
`0x4c`, `0x55` and `0x62`, read from `0x2000449a`, `0x2000449c` and
`0x2000449e`.  Those are calibration-shaped fields loaded earlier in the boot;
where the boot code gets them from is open.

One decompiler artifact to be aware of: the write of `0x8000` to register `0x40`
comes out of the decompiler as a one-argument call, `FUN_08022082(0x8000)`.  The
disassembly shows why — the compiler reuses a register, `movs r1, #0x40` then
`lsls r0, r1, #9` — and the register really is `0x40`, as the table says.  Do not
read the missing argument as "register 0".

**The 36-byte table** at flash `0x08024e40`, sent as 18 big-endian 16-bit words
to registers 2..19:

| reg | value | reg | value | reg | value |
|---|---|---|---|---|---|
| 2 | `0x6fc0` | 8 | `0xff33` | 14 | `0x5817` |
| 3 | `0x0e3d` | 9 | `0xc3fa` | 15 | `0x90a3` |
| 4 | `0xb041` | 10 | `0xa2a3` | 16 | `0x88f9` |
| 5 | `0xf770` | 11 | `0x8800` | 17 | `0x5800` |
| 6 | `0xf274` | 12 | `0x0603` | 18 | `0x415c` |
| 7 | `0x08f0` | 13 | `0x09fd` | 19 | `0x08a0` |

The BK4829's init has no equivalent block — that is one of the structural
differences between the two parts (see `ra89r_bk4829.md` for the register-by-
register comparison against the K1 tree).

## Other configuration in the same image

Two registers are written outside the boot init, and both name a role for this
chip:

| reg | who writes it | what it is |
|---|---|---|
| `0x75` | `FUN_08013790(band)` | band/mode select: the low six bits are rewritten to `0x09` (band 0), `0x11` (1), `0x0A` (2) or `0x12` (3); the bring-up asks for band 3 |
| `0x0c` | `FUN_08016228`, `FUN_08009CC4` | path switch: `0x0203` to enter the T/R state, `0x0a03` to leave it — the latter being exactly the value its own boot init writes |

An earlier version of this file said `FUN_080137D4` touches this chip; it does
not — that function is BK4829-only (`ra89r_bk4829.md`), and the BK4815's band
write is `FUN_08013790`.

The remaining per-band/mode routines are `FUN_080171D0` (10 writes),
`FUN_08005C34` (8), `FUN_08016CEC` (6), `FUN_0800B520` (6) and `FUN_08006D10` (5),
not yet extracted; they should be re-read against this chip's framing, since the
earlier list was built without separating the two register spaces.

## Open

1. **No driver.**  This chip is not driven by our firmware at all: the bus
   primitives in `firmware/App/driver/bk4829.c` are behind the BK4829's select,
   and `BK4815_CS_PIN` is defined but unused.  Adding it is a small step once the
   BK4829 is validated — the bit layer is already shared.
2. What this chip does versus the BK4829: it is the path the T/R switch takes for
   channels *above* 134 MHz, selected through register `0x0c`, with `0x75` as its
   band selector (`ra89r_rfpath.md`).  Why the crossover is 134 MHz is open.
3. The three RAM-sourced registers (`0x4c`, `0x55`, `0x62`): where does the boot
   code get those values?
4. Register semantics — extracted verbatim, not understood.
